# Adaptive calories

**Date:** 2026-08-30 · **Applies to:** `nouri-api` + `hybrid-pilot`
**Closes** item 5 in [the final migration matrix](../backend-migration/2026-08-29-final-migration-matrix.md) §7

---

## What it does

Given what someone actually logged and how their weight actually moved, it
answers: what should their daily calorie target be?

The method is energy balance run backwards. Average intake over the window,
minus the energy the weight change accounts for, estimates maintenance:

```
estimated TDEE = avg intake − (7700 kcal/kg × weight delta) / days
```

Their goal's offset is added to that, and the result is capped so a single
refresh cannot move a target by more than 150 kcal.

Around that sit the rules that decide whether there is an answer worth giving at
all: at least 14 complete diary days in a 28-day window, at least 5 weigh-ins,
at least 14 days between the first and last of them, and a change of at least
100 kcal before it is worth telling anyone about.

---

## Where it runs

**`nouri-api`**, at `POST /v1/adaptive/refresh`.

It used to run on the device. The app fetched a month of diary days, a month of
entries and a month of weigh-ins, computed the recommendation locally, and
POSTed it back — six round trips, and a window between the reads and the write
in which any of the three inputs could change. A recommendation could be
computed from data the writer never saw.

Now the analysis and the write are one transaction on one machine.

The app keeps exactly one piece: `applyAdaptiveRecommendationToTargets`. That is
the *apply* step — turning an accepted recommendation into a calorie allowance
and per-day overrides — and it is a profile edit the user triggers, so the app
has to know what it is about to save before it saves it. It is pinned by the
shared conformance corpus.

## How the port was verified

Not by review. By diffing.

A dual-run harness loaded both implementations side by side and compared every
field of every output across **generated scenarios that sit on every threshold
the engine has**: 0–30 complete days, 0–12 weigh-ins, spans either side of the
14-day minimum, all nine goal/strategy pairings including a deliberately
inconsistent one, and calorie allowances walked across the interesting range
including "not set".

Two coverage guards kept the diff honest:

* Every outcome status — `disabled`, `insufficient`, `unchanged`, `ready` — had
  to be produced by at least one scenario, or the run failed. `unchanged` was
  not reachable by chance (it needs a target already within 100 kcal of the
  recommendation), so scenarios were generated by running the engine once and
  parking the allowance next to its answer.
* The harness skipped rather than passed if the other repository was absent.

**Result: zero differences.**

Then the diff was itself checked, by mutating the backend copy one change at a
time:

| Mutation | |
| --- | --- |
| `ADAPTIVE_KCAL_PER_KG` 7700 → 7716 | caught |
| `ADAPTIVE_MAX_DAILY_SHIFT` 150 → 200 | caught |
| EMA smoothing 0.35 → 0.34 | caught |
| `day.date <= asOfDateKey` → `<` | caught |
| `localDate >= windowStart` → `>` | caught |
| high-confidence threshold 24 → 25 days | caught |
| `ADAPTIVE_MIN_RECOMMENDATION_DELTA` 100 → 99 | **missed**, then caught |
| weigh-in tie-break `>=` → `>` | **missed**, then caught |

The two misses were gaps in the *scenarios*, not in the engines, and both were
worth finding:

* **The 100 kcal floor.** Targets snap to a 50 kcal step, so when the allowance
  is also a multiple of 50 the delta can only ever be a multiple of 50 — and any
  threshold in (50, 100] behaves identically. Only an unaligned allowance can
  tell 100 from 99 apart. Real users have unaligned allowances; the scenarios
  did not. Offsets of ±49, ±51, ±99, ±101 were added.
* **The weigh-in tie-break.** It only fires when two readings share a
  `measuredAt`, and only distinguishes `>=` from `>` when they *also* share an
  `updatedAt`. The scenarios had same-day readings at different times, which
  both operators handle identically. A full tie was added.

## What holds it now

The mobile engine has been deleted, so there is nothing left to diff against.
Three things replaced it:

**The shared conformance corpus**, which gained five suites — `resolveGoalStrategy`
(8 cases), `getGoalCalorieOffset` (9), `estimateAdaptiveTdee` (5),
`getAdaptiveRecommendationConfidence` (10), and
`applyAdaptiveRecommendationToTargets` (7) — plus
`buildAdaptiveRecommendation` (15), which records **whole outcomes**.

Those 15 expectations were recorded from the *mobile* implementation, at the
moment the dual run had just shown the two agreed. The mobile copy is gone; its
answers are not.

They are written as compact scenario descriptions — "20 complete days at 2000
kcal, 8 weigh-ins over 21 days from 82 kg to 81 kg" — which both repositories
expand with the same arithmetic. Recording several hundred literal rows per case
would have added 228 KB to a corpus that is mirrored, checksummed and reviewed
in diffs; this is 9.6 KB and legible.

**The mobile conformance runner** declares the three suites it no longer
implements in a `BACKEND_ONLY_SUITES` list. Its coverage check still fails for a
suite that is merely forgotten — adding a name to that list is a decision
someone has to write down.

**Ten end-to-end tests** (`test/adaptiveEngine.test.ts`) covering everything
between the engine and the database: that the loader hands it the right rows,
that dates survive as calendar days rather than timestamps, that the result is
stored once, that RLS scopes it to the caller, and that the window ends at the
last complete day rather than today.

## Two things the verification found

### Three queries on one connection

`loadAdaptiveInputs` originally issued its diary-day, entry and weight queries
with `Promise.all`. `UserDb` wraps one pooled connection inside one transaction,
and a single `pg` client cannot run concurrent queries — the driver warned
(`client is already executing a query`) and serialised them.

The backend suite passed both before and after the fix. Running the real app
against the real database is what surfaced it. Three round trips on an
already-open connection cost far less than the correctness of the answer.

### Clearing per-day calorie overrides returned 500

Accepting a recommendation set the new calorie allowance and then failed:

```
[nouri-api] PATCH /v1/me/settings failed: INTERNAL_ERROR status=500 requestId=360fda70…
```

The user saw *"Could not apply recommendation"* while their target had already
changed — a half-applied write.

`JSON.stringify(null)` is the string `"null"`, which `::jsonb` parses to a JSON
null: a value, not an absence. `jsonb_typeof` then reports `"null"` rather than
`"array"`, and the column's `user_settings_daily_overrides_is_array` check
rejects the row. Binding SQL NULL is what "clear these" means; the
"not supplied" versus "explicitly cleared" distinction is carried by a separate
presence flag, which is why `== null` is correct here and `=== undefined` was not.

This was **pre-existing and unrelated to the engine** — clearing overrides had
always failed. It surfaced now because `applyAdaptiveRecommendationToTargets`
returns `dailyCalorieOverrides: null` for every user who has none, which is most
of them. Two tests now cover clearing and not-mentioning.

That diagnostic line is the one added in the previous task. Without it the
symptom was "Please try again".

## Verified end to end

A 28-day window was seeded into the local database — 20 complete days at 2000
kcal, 8 weigh-ins over 21 days from 82.0 kg to 81.0 kg — and the real app was
run against it on the emulator:

| | |
| --- | --- |
| Estimated TDEE | **2327 kcal** |
| Trend | 82.0 → 81.252 kg (**−0.249 kg/week**) |
| Confidence | medium (20 days, not the 24 that "high" needs) |
| Goal | lose fat, light deficit (−275) |
| Recommendation | 2327 − 275 = 2052 → **2050** after the 50 kcal step |
| Current target | 1900, so the +150 delta is at the cap |
| Stored | `proposed`, `algorithm_version: v1` |

The app showed *"Current base target 1900 kcal/day. Suggested target 2050
kcal/day (+150 kcal). Confidence: medium. Next review Sun, Sep 6."* — computed
by the server, with the client engine deleted. Accepting it set
`calorie_allowance = 2050` and marked the recommendation `applied`.

The smoothed trend is worth noting: the readings fall a clean 1 kg over 21 days,
but the EMA reports −0.748, because a smoothed series lags a linear one and its
first point is the first raw reading. That lag is the point — it is what stops a
single heavy morning moving someone's calorie target — and it is exactly the
kind of behaviour a "tidied up" port would quietly lose. The port was made
line-for-line rather than improved, for that reason.
