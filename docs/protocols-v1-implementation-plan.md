### Ownership and deletion

Installation/delivery ownership, cancellation and deletion rules in this section apply when the deferred notification tables are introduced. Current course/phase/log/reminder and all-Protocol mutations must work without those tables or notification helpers. Keep all non-notification cascades and ownership checks now.

Follow existing parent-based RLS for phases, occurrences and results; own-row policies for courses/logs/panels/reminders/preferences/installations. Where `user_id` is also stored on a child, enforce `(course_id, user_id)` consistency with a parent unique key and composite FK. RLS alone does not stop a user's child row referencing a different user's parent when foreign-key validation sees that parent. Cover same-user cross-course mismatches as well as cross-user access.

Grant the backend only required operations, catalog SELECT only, with explicit revocation of direct client privileges and appropriate catalog read policies. Delivery tables also require RLS: request-path reads/cancellations remain owner-scoped, while cross-user worker access has separate explicit policies. Test grants on real Supabase; baseline defaults/grants do not automatically grant the backend access to new tables/sequences. Do not grant application roles catalog writes to simplify seeding. New operational worker grants are separate and narrow.

Course deletion must atomically cascade through its phases, occurrences, logs and pending deliveries, while preserving bloodwork, nutrition and weights. Phase deletion is different: a phase/log relationship must prevent a future-phase replacement from cascading away recorded reality. Restrict removal of referenced phases/occurrences during schedule mutations; reject a conflicting operation atomically instead of deleting a log. The course-deletion service can explicitly order dependent deletion in one transaction where restrictive FKs require it. Verify the FK design also permits the existing `auth.users → profiles` account-deletion cascade to remove all owned Protocol/bloodwork/installations/deliveries; test this database path without introducing a new account-deletion product flow.

**Recommended all-Protocol deletion scope:** courses/logs/sites derived from them, reminders/deliveries, bloodwork panels/results, marker preferences and opt-in/introduction settings. The confirmation must explicitly name bloodwork. Keep catalogs, nutrition, ordinary bodyweight and unrelated user settings. General installation registrations may remain, but there must be no remaining Protocol deliveries. Disabling only hides the feature and suppresses future pushes; it preserves history. These user-facing choices require confirmation in the product contract, not a guessed behavior in a DELETE handler.

### Planned versus actual is an end-to-end contract

An occurrence is the plan. A dose log is reality. Every DTO and logging form must keep both visible, using separate `planned` and `actual` fields or equivalently explicit names. The server reads planned values from the occurrence, not from the logging payload.

For a Monday 20:00 E2D occurrence logged Tuesday 09:10 at a different amount:

- Monday's occurrence ID, planned 20:00/amount/route and phase remain unchanged.
- The log stores Tuesday 09:10 and the actual amount/route; Wednesday remains Wednesday 20:00.
- Calendar completion stays attached to Monday's occurrence. Injection history and PK use Tuesday's actual instant.
- Historical unlogged occurrences contribute **nothing** to PK. Do not substitute planned doses when history is incomplete.
- Deleting the log restores the occurrence's derived state; on a historical date it is Unlogged. PK and site recency lose that actual administration.
- A future scheduled occurrence that already has an early actual log must not contribute twice to a future projection.

Use `actualRoute` to select a logged dose's model and `plannedRoute` for projections. Remember route/site from the user's recent actual logs, filtered for compatible route/site, as editable defaults. Keep original planned fields visible when defaults differ; do not persist another authoritative site-history table or an injection recommendation.

### Recurrence and atomic edits

Implement one pure compiler in the API. Inputs include a phase timeline, bounded interval, phase timezone and explicit testable clock where needed; outputs contain deterministic planned slots. Use it for preview, activation/backfill, horizon extension, phase edits and Compare. PRN yields no occurrences. Preview/Compare produce no writes and use preview slot keys rather than pretending to have persisted occurrence IDs.

Daily/weekdays/E-N-days use phase-local calendar arithmetic. Every-N-hours uses elapsed time from an offset-bearing anchor instant, not local-day arithmetic or the latest actual log. Use Monday-first indices consistently with existing Nouri helpers and document them in the schema. One-time schedules require an absolute resolved instant. Multiple daily/weekday slots retain individual amount/unit/time; do not collapse them to one course dose.

Store resolved instants as `timestamptz` and retain phase IANA timezone. Reuse the local Protocol compiler's explicit gap-forward/fold-earlier resolution and its independently reasoned fixtures. The older diary two-pass converter is not a substitute for this behavior; avoid changing diary semantics incidentally. Native forms should preserve unchanged absolute anchors and use `/time-preview` for edited civil times. A narrowly scoped timezone dependency is justified only if the current implementation cannot satisfy required fixtures reliably.

Use half-open phase intervals `[effective_from, next_effective_from)` and a documented exclusive course-end boundary. Date-only end selection should include that calendar day by resolving to the next local midnight. Capture one server cutoff per mutation. Lock the course consistently for activation, phase insertion/replacement, end, logging and materialization; validate expected revision before changing the timeline. This prevents a concurrent log being removed between an unlogged check and regeneration.

Activation commits the course/phases and occurrences from the past start through the 120-day future horizon together; it creates no historical logs or old notifications. Reject over-budget preview/backfill requests before any partial activation, with a clear technical range/density error. Agree on computational limits in Stage 0; they must not masquerade as medical dose limits.

For a schedule change, preserve all historical occurrences, including unlogged ones, and every logged snapshot. Diff affected future unlogged slots, preserving IDs for unchanged slots and removing/replacing only changed ones. Default to keeping later phases. Replacing later phases requires the explicit choice, cancels their pending deliveries in the same transaction, and cannot remove referenced logs. Do not use `ON CONFLICT DO UPDATE` to rewrite historical planned fields.

Materialize idempotently through 120 days from now, including future-start courses when they enter the horizon. A persisted future course or phase beyond the horizon is still visible as planned; preview/projection can compile farther without persisting an infinite calendar. A daily job extends the horizon; a bounded repair path can restore missing coverage when a user explicitly starts/changes a course. Calendar responses distinguish outside-materialized coverage from an empty schedule; Stage 0 must define extended-calendar behavior instead of returning misleading empty months.

Materialization needs deterministic uniqueness, bounded course batches, restart-safe progress, course locks and a visible failure/coverage metric. Expired finite courses transition to ENDED consistently; reads must not depend on the job being punctual to know that their end has passed. Do not preload 120 days of native scheduled notifications: a change/log from another device could not reliably cancel them.

Deferred delivery flow — retained for Stage 8b:

1. Persist one logical delivery intent per occurrence/reminder and target installation, with a unique key. New device registration must not trigger historical pushes.
2. Claim due intents transactionally with a lease/`SKIP LOCKED` approach. Recheck live occurrence, log absence, course/feature notification settings, installation ownership, end boundary and scheduled time.
3. Commit the claim before external HTTP. Send with bounded timeout and the opaque target ID; no actual dose or lab values in metadata. The visible compound/planned amount copy in the spec needs an explicit lock-screen privacy decision.
4. Persist acceptance/ticket/outcome, poll receipts, disable invalid tokens, and retry only according to the agreed delivery semantics. Do not treat provider acceptance as proof of device display.
5. Phase/end/delete/log/disable mutations cancel unsent eligible intents atomically. A delivery already handed to a provider cannot be reliably recalled. Deleted-log history does not resurrect a past notification.

**Deferred decision: exactly-once delivery, required only when notifications resume.** PostgreSQL uniqueness prevents duplicate intents and ordinary job replay, but cannot atomically commit an external push handoff. Expo explicitly describes best-effort, at-least-once provider delivery with possible duplication or loss: [Expo delivery guarantees](https://docs.expo.dev/push-notifications/faq/#delivery-guarantees). A send accepted just before a crash leaves an ambiguous outcome; blindly retrying can duplicate, marking sent first can lose it. Proposed V1 acceptance is one logical reminder, no deliberate repeats, deduplicated normal retries, and an explicit unknown-outcome policy. If duplicate avoidance takes priority, do not auto-retry unknown outcomes, acknowledging possible loss. Product must resolve this conflict before claiming the spec's guarantee is met.

Notification action/tap only opens the app. Wait for auth hydration/navigation readiness, fetch the current occurrence using its opaque ID, then open the confirmation sheet. Cold start, logged/deleted/changed occurrence, disabled feature, expired session and a different signed-in account all need safe outcomes. Never trust notification payload values as the logging form's source of truth, and never log from a background action. Deduplicate response handling so a cold-start payload plus listener does not open two sheets.

Token ownership must follow account changes and sign-out, including failed deregistration. Decide how server-side registration/session revocation prevents an old account's push reaching a shared installation; merely clearing mobile state is insufficient. Define multi-device policy and delivery uniqueness together: one notification per enabled installation is a proposal, not yet stated by the spec. Also define due-time grace/TTL so an outage does not create an indefinite overdue push backlog.
